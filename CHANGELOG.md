## [Unreleased]

### Added

- **A recipe produced by freezing a discovery** (`targets/tga-artg.json`, ticket #9): the keyword `vitamin d` typed into the TGA's public ARTG register search and submitted, with the observation it was written from committed beside it (`targets/tga-artg.observation.md`) — the query page and the results page as observe mode reported them, what the recipe is, and why each step looks the way it does. The recipe is the first *production* target in the repository rather than a verification asset; the `targets/README.md` now says which is which. Nothing in the plugin changed, so this is not a new version: `targets/` is not in the published `files`.

- **The `type` verb** (targets): `{ "verb": "type", "candidates": [ … ], "value": "维生素D" }` writes a value into the first reachable field that takes text — by selector, by the words a person reads, or by role and accessible name — and makes the page *hear* it: the field is focused, the value goes in through the **prototype's** `value` setter (assigning the element's own property updates a framework's tracker at the same time, so the change looks like no change and the page never reacts), and `input` + `change` are dispatched. It replaces what the field held rather than appending, refuses a control that takes no text (a checkbox, a native `<select>`, a `file`/`range`/`color`/`hidden` input) and a field that is read-only, disabled or unreachable, and then **reads the value back** after a frame: a controlled component can take the change and re-render the old value, so `"维生素D" was written into it (it held "") and it now holds "" — the page did not take it` fails the fetch instead of letting a search run with an empty box. What the page *does* with the value is the `waitFor` that follows.

- **`waitFor` can wait on state** (targets): `{ "kind": "state", "state": "checked" | "unchecked" | "enabled" | "disabled", "candidates": [ … ] }` holds when every control the candidates name is in that state — the condition text cannot express, because a gate that refuses to continue until all five consents are ticked says so in no label at all. The scope is the first candidate that names a control which can *answer* (the same ordered-candidate rule every verb follows, so a fallback cannot silently widen the set), controls that hold no such state are dropped rather than counted as "not checked" (a text field's `checked` is always `false`), and reachability is deliberately not asked — a hidden 1×1 checkbox under its own label is exactly what a gate uses, and whether it is checked has nothing to do with whether a person could click it. The state read is the one `check` verifies with. Nothing matched is not a failure yet (the page may still be rendering), so the poll keeps asking until the step's budget runs out and then fails with what it saw rather than a bare timeout — `all checked over selector "input[type=checkbox]": 3 of 5 controls in selector "input[type=checkbox]" are not checked (e.g. "全选")`. Each read is bounded by what is left of the step, so a stalled page cannot outlive the step's ceiling — and the last thing the page actually said is what the failure reports, so a final poll that runs with almost no budget left cannot erase the count before it.

- **The `check` verb** (targets): satisfy a precondition by putting a control into a state, in the way a person does it — `{ "verb": "check", "candidates": [ { "text": "全选" } ], "state": "checked" }` (`state` omitted means `checked`). It resolves through the same walk `click` uses, with one addition the real gate forced: a control that occupies layout but cannot be hit because the page draws something over it (booking.com's consent boxes are 1×1 px inputs under a 897×20 `<label>`) falls back to the `<label>` that forwards a click to it — which is the part a person clicks. It is **idempotent** (a control already in the wanted state is not toggled off) and it **reads the state back**: the step passes only when the control *reports* the wanted state afterwards, waiting a frame for the page to react first, so a control the page reverts (a React-owned input, measured) fails the fetch naming the step, the verb, the candidate and the URL instead of pretending the precondition holds. `aria-checked` and `aria-pressed` are read the same way for custom controls, and a control that holds no state at all (a text field, a button) is refused rather than called unchecked.

- **The `click` verb** (targets): a click names an intent and an **ordered candidate list** — a CSS selector, a visible text, or a role with an accessible name — and the first candidate that is *reachable* is the one clicked; once an earlier candidate is reachable the later ones are not tried. Reachability is verified **before** the click (it exists, it occupies layout on its own or through the `<label>` that forwards a click to it, nothing else sits on top of it, and it is not disabled), and an attempt where every candidate is passed over fails the fetch with `WEB_FETCH_ACTION`, naming the step, the verb, every candidate it tried and why, and the URL at that moment — "a click was dispatched, so it must have worked" is not accepted here. The click deliberately does not assert its own effect: what a click does differs per page, so the `waitFor` after it is the assertion — and it only counts when it actually changed, because the condition is read *before* the click as well (a wait that already held proves nothing about the click). A click no `waitFor` confirmed is marked **`clicked (unverified)`** in the action summary, so ending a recipe on a click shows the gap instead of hiding it. Text candidates work in Chinese and English, names are compared as a person reads them (trimmed, collapsed, case-insensitive), and a click that navigates the page away is reported as a click rather than as an unreachable control.

- **Targets** (`targetsFile`, blank by default): a JSON file of named recipes that tell one URL how to be fetched — an exact or prefix URL match, then an ordered list of steps whose post-conditions must hold before the document is read. Selection is by the URL that was *asked for* (the fetch seam carries nothing else), the longest match wins, two equally specific matches are a configuration error rather than a coin toss, and no match is an ordinary fetch. The verbs are `waitFor` (visible text appearing or disappearing, a URL, or a fixed wait) and `click`; a step that does not hold fails the fetch with `WEB_FETCH_ACTION` naming the step, and an unreadable, malformed or ambiguous file fails it with `WEB_FETCH_TARGET` naming the JSON path of the problem. When a target runs, the body opens with a one-line action summary and `url`/`statusCode` describe the document the actions ended on — the result shape is closed (ADR-0003), so the body is the only channel that can say so. A match URL may not carry a query string or hash — comparison ignores both, so writing them would widen the match silently — and a target that matches a response which is not a document (a JSON endpoint, say) fails with `WEB_FETCH_TARGET` rather than being skipped in silence. A fixed wait longer than the remaining budget fails instead of sleeping what it can and reporting success. Pages that match no target behave exactly as before.

- **Observe mode** (`observe`, off by default): instead of denoised prose, the fetch returns the page's *actionable state* — the reachable controls with their labels and states, complete counts, and the head of the visible text. It exists because of what a real gate exposed: booking.com's consent interstitial lists five consents, has a select-all, refuses to continue until every one is ticked, and says none of that in any label a heuristic could read. The same report is where the whole story is legible — `checkboxes 5 (unchecked 5)`, each labelled by the `<label>` a person would click, the select-all among them, the accept button enabled, and `covered` on the five inputs, because they measure fine yet something sits on top of them, which is exactly why an actionability-checked click times out on them. A *mode* rather than a per-fetch option because the fetch seam carries only a URL. Reading the state is the whole point, so a page that cannot be read fails the fetch (`WEB_PROVIDER_ERROR`) instead of returning an empty observation.

- **Consent-banner dismissal** (`dismissConsent`, off by default): after the page settles and before it is read, the fetch clicks the "accept all" control of the consent managers this plugin knows — OneTrust, TrustArc (measured on cn.iherb.com, where the banner renders `#truste-consent-button` labelled 全部接受), Cookiebot, Didomi, Osano, Usercentrics, CookieYes, Complianz, Iubenda, Klaro, Google Funding Choices, and Quantcast, plus an `aria-label`-based last resort. The probe is one `evaluate` (the abstraction's existing scripting seam, already used by the challenge probe, and still optional — a backend or fake without it simply skips the step); it walks the selectors in order, clicks the first control that is actually laid out, and clicks at most one element, so a site running two consent managers cannot be double-answered. Every selector names an accept-all control: one that could be a reject or manage control is deliberately absent, because guessing wrong would record a *rejection* on the user's behalf. The named managers are the precise candidates, not the whole rule: when every one of them misses, a trailing **text candidate** clicks any control whose accessible label is exactly "accept all" / 全部接受 in either language — but only inside consent-looking UI (a dialog, a consent-named ancestor, or a fixed/sticky overlay), because an "Accept all" button in a checkout form is not consent UI and a wrong click writes a rejection retrying cannot undo. Labels match by equality, never by substring, so "accept necessary only" and "accept and continue to checkout" are left alone;  roles are how the control is found (`[role=button]` and submit inputs are eligible), not a separate candidate kind. Consent UI comes in two shapes, and the fourth signal covers the second: a **full-page consent interstitial** (measured on booking.com, whose gate is `/pipl_consent.zh-cn.html` titled 需您同意 with a bare `<button>同意</button>` that has no consent-named ancestor at all) has none of the three box signals, so the rule also accepts a control when *the document itself* is the consent UI — its URL or title matching the consent vocabulary — and only while the document is short, so a long content page that merely mentions consent cannot license a click. The provider then re-describes the result from the settled document: accepting an interstitial sends the browser back to the page it interrupted, and reporting the gate's URL and status next to the accepted page's content is exactly the mismatch the action-model design forbids. It is off by default because the click is not neutral — it records the user's consent in whichever profile the fetch runs in, the real one on the CDP and DSH-managed backends — and it is best effort in every direction: no banner, no `evaluate`, a stalled probe (bounded at 3s), an unparseable answer, and a click that throws all leave the fetch's own outcome untouched, with at most a warning on stderr.

- **Outbound proxy support** (settings card → *Playwright 网页爬取*): `proxyServer` (`host:port` or an `http(s)/socks4/socks5` URL), `proxyBypass`, `proxyUsername`, and `proxyPassword`. The proxy is injected into every browser this plugin launches — the local per-fetch browser and the new DSH-managed persistent browser — through Playwright's `launch({ proxy })` / `launchPersistentContext({ proxy })`, with `127.0.0.1`/`localhost`/`::1` always merged into the bypass list (`PROXY_LOOPBACK_BYPASS`). A `user:pass@` in the address or in an upstream launch error never reaches a message: failures are reported as the provider-specific `WEB_FETCH_PROXY` code naming the proxy address (userinfo stripped) and where it was resolved from. The password field renders masked.
- **DSH-managed persistent browser backend** (`backend: managed`): DSH calls `launchPersistentContext(userDataDir, { headless, proxy, args })` once and keeps that one browser for the provider's lifetime, so logins, cookies, localStorage, and extensions survive across fetches, plugin reloads, and `dsh web` restarts. Each fetch is a tab in the persistent context (the browser and its context are never closed per fetch — only tabs are — and teardown closes the browser while leaving the profile directory on disk). New settings: `headless` (default `true`), `userDataDir` (blank = `$DSH_HOME/web-fetch-playwright/profile`), and `launchArgs` (extra Chromium arguments, shell-style split, applied to every plugin-launched browser). A launch descriptor that changes (profile directory, headless, args, proxy, Playwright path) replaces the browser on the next fetch; a browser the user killed is detected and relaunched. `maxConcurrency` means **concurrent tabs** (default 50) on this backend, exactly like CDP.
- **`dsh-web-fetch-launch`** (`bin/launch-browser.mjs`): the local GUI/tunnel launcher for the topology where the visible browser runs on your workstation and the plugin attaches over CDP. It reads the SAME `web-fetch-playwright` settings section the card writes, copies your real profile to a throwaway directory (excluding `Singleton*` locks, `Cache`/`Code Cache`/`GPUCache`/`Service Worker`/shader caches, and crash droppings; cookies, `Login Data`, `Local Storage`, `Preferences`, and extensions are kept), refuses a destination a browser is already running on, and builds/runs your browser with `--remote-debugging-port=9222 --remote-debugging-address=127.0.0.1 --user-data-dir=<copy> [--headless=new] [--proxy-server=… --proxy-bypass-list=…]`, then prints the `autossh -M 0 -N -R 9222:127.0.0.1:9222 <user@server>` line. `--dry-run` prints instead of launching; flags (`--browser`, `--profile`, `--user-data-dir`, `--proxy`, `--proxy-bypass`, `--launch-args`, `--headless`/`--headful`, `--port`, `--address`, `--settings`, `--no-copy`, `--force`) win over settings. The settings card gains a read-only preview of that command, rendered by the same argument builder the launcher uses. An EXISTING copy target is refused unless `--force` is passed (a destination a browser is running on is refused even with `--force`), `--address` accepts loopback only (`127.0.0.1`, `127.0.0.0/8`, `::1`, `localhost`; a bracketed `[::1]` is normalized to `::1`), and every echoed argument and error message goes through credential scrubbing before it reaches stdout/stderr.
- **Shared-browser pool** (`src/browser-pool.ts`): the CDP pool's lease/liveness/replacement machinery generalized over an injectable opener and key, so the CDP and DSH-managed backends share one implementation. `CdpConnectionPool` is now the CDP instantiation of it and keeps its public API and behavior (its 15 tests are unchanged).
- **Per-fetch network capture** (`recordNetwork`, off by default): every fetch opens ONE CDP session on the tab it just created and records that tab's XHR/Fetch/WebSocket traffic — request URL/method/headers/payload, response status/headers/body, WebSocket lifecycle and frames — streaming `network.jsonl` (one JSON object per line, appended while the fetch runs) and exporting HAR 1.2 as `har.json` when the fetch ends. Both files live under `<recordDir>/<sessionId>/` (default `<working directory>/net-dumps`, gitignored), with the directory at mode `0700` and every file at `0600`. New settings: `recordDir`, `captureBodies` (default `true`), `maxBodyBytes` (default `262144`, `0` = no cap, ceiling 16 MiB) and `recordAllResources` (default `false` — image/font/media/stylesheet records are dropped). Extra-info headers/cookies are paired per redirect hop by that hop's own identity (`:path` + `:authority` for a request, the status for a response), so a hop with no extra-info event of its own — a cached 301 — keeps its own (empty) header set instead of inheriting the next hop's credentials; the fallback and its limits are documented in `src/recorder.ts` and the README. Recording is best-effort throughout: no capture or write failure can fail a `web_fetch`, and the HAR is exported on success, on a thrown error, on abort and on plugin teardown. `src/har.ts` holds the pure HAR 1.2 assembly (WebSocket frames ride Chrome's `_webSocketMessages` extension).
- **Offline capture→crawler pipeline** (`tools/netdump/`, Python 3.11 standard library only): reads a plugin JSONL dump or any HAR 1.2 (including flat single-line records), filters static resources (image/font/media/stylesheet/script, static extensions, HTML documents) and ranks the remaining business APIs into `endpoints.json` — `method`, `urlTemplate`, `sampleUrl(s)`, `requestHeaders`, `query`, `bodyShape`, `callCount`, `score`, `scoreFactors`, `rankReason`, plus a `filtered` list with reasons and WebSocket channels grouped separately — then emits a runnable `crawler.py` with the captured headers/cookies embedded, `httpx.AsyncClient(http2=True)`, a real `asyncio.Semaphore` around the request, exponential backoff with jitter and `Retry-After`, `--proxy`/`--proxies-file` rotation, resumable JSONL output (per-line `flush`+`fsync`, half-written lines repaired), a SECURITY WARNING header, and output directories/files at `0700`/`0600`. `netdump build` and `netdump summary` share the CLI; the summary deliberately prints no credentials.

### Changed

- A `waitFor` whose read does not come back no longer says so in the failure message. The last poll of a long wait runs with no budget left, so a text condition that was simply not there could be reported as "the page did not answer" about a page that had answered forty times; the message is now the honest "not met within Nms", while an `absent` condition still cannot be satisfied by a read that did not happen.

- **The CDP backend no longer refuses fetches when `proxyServer` is set.** A proxy is a launch-time property of the browser process, and a CDP browser was started elsewhere: the plugin injects nothing there and verifies nothing there (a browser started without `--proxy-server` simply egresses directly), so it explains the relationship in the card copy, the README, and the CDP error messages instead of blocking the fetch. The decision lives in one constant (`CDP_PROXY_POLICY`). `WEB_FETCH_PROXY` remains for the two paths this plugin can actually observe: an unusable proxy value, and a launch that failed with a proxy configured.
- The local backend honours `headless` (previously always headless) and `launchArgs`, and the launcher shares the same `--headless=new` switch.
- Documentation: the README (en/zh) gains the proxy chapter, the DSH-managed backend notes, the two-topology manual (visible browser + `autossh` tunnel), and the launcher reference; `SECURITY.md` distinguishes the backends (per-fetch fresh context vs. a persistent profile) and documents proxy/profile/credential handling; `package.json` ships `bin/` and its `dsh` disclosure lists the proxy, the persistent profile, and the launcher's spawn; `docs/end-to-end-acceptance-manual.md` walks a real machine through P0→P3 (settings, both topologies, `autossh`, capture, netdump, server-side crawler run) with expected outputs, troubleshooting, and the list of steps that still need a real browser/proxy/tunnel.

### Fixed

- **Consent dismissal reported "clicked" as if it were "done", and could return the gate as the page.** A full-page consent interstitial was recognised and its accept control was clicked, but nothing verified the outcome: on a gate that ignores the click (measured on booking.com, whose 同意 button does nothing until its own five consents are ticked — an interstitial with hidden `<input>`s whose visible hosts are their labels) the fetch went on to read the *gate* and return it as if it were the page the caller asked for. A gate click is now verified: the page is asked whether it is still the gate, and a gate that did not clear ends the fetch with the provider-specific `WEB_FETCH_CONSENT` code naming the URL, instead of a plausible-looking page. Only a gate click is checked — a banner dismissal costs no second probe and cannot fail a fetch.

- **A denoised fetch could return a cookie banner as the page's content.** Readability signals failure by returning `null`, but it also *succeeds* on pages it cannot read: on a live iHerb product page it returned the 278-character consent block out of an 18,639-character document, so the null fallback never fired and 27,967 characters of product copy, spec table, and image links were replaced by a cookie banner. A Readability result is now discarded when it is both small in absolute terms (<2,000 characters) and a sliver of the document (<15% of its text). The thresholds sit an order of magnitude away from both measured classes — broken: 0.015 and 0.0003; healthy: 0.59 (playwright.dev) and 0.45 (MDN) — and a short extraction on a short page still wins, as does any extraction over 2,000 characters. The whole-document fallback then returned the full product page under mode `document`. Alongside it, non-content subtrees (`script`, `style`, `noscript`, `svg`, `template`) and HTML comments are deleted from the rendered HTML *before* it is charged against the 2,000,000-character pipeline budget: on that same page they were 1.8 MB of a 3.2 MB document and the product copy began past the cap, so the old raw slice beheaded the article first. The budget now measures content rather than bloat, which also means a stripped-but-uncut page is no longer flagged `truncated`.
- **A fetch queue longer than `maxConcurrency` stranded its tail.** `release()` handed the freed slot to the next waiter without dropping the finished holder's count, so the active count drifted one above the limit and only every other release started a waiter — a 20-fetch burst at `maxConcurrency: 4` completed 8–10 and failed the rest with `WEB_FETCH_TIMEOUT` after 20s. Regression-tested.

- **The launcher's profile-copy guard is actually wired to the CLI.** `copyProfile` already knew how to refuse an existing destination, but `bin/launch-browser.mjs` never asked it to: pointing `--user-data-dir` at an existing directory silently merged into it. The entry path now passes `{ force: flags.force === true }`, `--force` is a real flag (usage + parser), and a re-run without it fails with a readable error instead of touching the directory; a destination a browser is running on stays refused even with `--force`. The whole argv→settings→plan→copy→run sequence moved into the exported `runLauncher`, so the test suite drives the real entry (and the real `bin` when a build exists) rather than a hand-copied call order.
- **Launcher diagnostics no longer leak credentials and the DevTools port can no longer be bound to a network interface.** Every echoed argument and error message goes through `scrubCredentials` (removes each token's userinfo up to its LAST `@`, so passwords containing `/` or `@` are covered; unknown flags, `--port`, `--address` and plan failures alike). `--address` accepts only `127.0.0.1`, `127.0.0.0/8`, `::1` or `localhost` and refuses anything else with the reason; a bracketed `[::1]` is normalized to the bare `::1` Chromium needs and the bracketed form is never passed through.
- **Launcher settings parsing matches YAML.** Double-quoted scalars are unescaped (`\\`, `\"`, `\n`, `\t`) and single-quoted scalars fold `''` to `'` (`` 'it''s' `` → `it's`), so a password or path with an escape is read the way YAML defines it.
- **Capture robustness.** A malformed URL or record now degrades to that record alone — the HAR export never loses the rest of the document; per-hop `requestExtra`/`responseExtra` rows are written when the extra is claimed; each capture claims its own `<sessionId>` directory with a non-recursive `mkdir` (two captures can never share a dump); and capture problems are reported (report + a rate-limited plugin log) instead of disappearing.
- **Extra-info pairing no longer attributes a hop's credentials to another hop.** Pairing is by the hop's own identity (`:path` + `:authority`, plus the status for responses) with an explicit arrival-order fallback only when no identity is available, so a cached 301 with no extra-info event of its own can no longer inherit the next hop's cookies/`Authorization`; the fallback's preconditions and the two remaining exceptions (a response extra whose status matches no hop; consecutive hops sharing a status) are documented in `src/recorder.ts` and the README and covered by synthetic-event tests.
- **`api-over-static-extension` is reachable without `_resourceType`.** A static type *inferred* from a HAR's extension/mime fallback is weak evidence, so a URL that looks static but returns JSON is kept and flagged (`rankReason: api-over-static-extension`) even when the capture did not carry `_resourceType`; a type the capture states explicitly (Chrome `_resourceType`, CDP `type`, plugin JSONL `resourceType`) stays hard evidence and is filtered as before.

## [0.2.7] - 2026-09-06

### Fixed

- **Boot no longer fails against dsh-settings 0.1.2+** (`dsh web` died with `plugin tree failed to load … The requested module '@deepseek-ai/dsh-settings' does not provide an export named 'installSettingsSection'`). The plugin was built against the 0.1.1-era API whose top-level helpers (`installSettingsSection`, `settingsNamespace`) no longer exist: dsh-settings 0.1.2 moved that behavior onto the settings service itself (`ctx.settings.installSection(owner, ns, schema, entry, hooks)`) and replaced the runtime `settingsNamespace()` factory with the plain `SettingsNamespace` string type. The host resolves a plugin's bare `@deepseek-ai/*` imports against its own module graph (the loader imports entry packages with the host context as resolution parent), so the plugin's local 0.1.1-rc.1 copy never shields it — the moment the host runs dsh-settings ≥0.1.2, ESM's strict named-export check kills the whole plugin tree at link time. `apply()` now follows the same idiom as the shipped providers (see `web-search-deepseek`): the namespace is a literal constant and the section installs through `ctx.inject(['settings'], (settingsCtx) => settingsCtx.settings.installSection(...))`, so `lib/index.js` no longer imports `@deepseek-ai/dsh-settings` at runtime at all. Dependencies were aligned to the host generation: devDependencies to `0.1.2-alpha.5` (plus `@deepseek-ai/dsh-client-store`, which the published ui-slots types import but do not declare — without it `InjectFace`'s `HostObservable` inference silently degrades to `any` and `card.tsx` fails typecheck), `@deepseek-ai/schemastery` to `>=3.18.2`, and the dsh-settings/dsh-web peer ranges tightened to `>=0.1.2-alpha.0 <0.3.0` (older hosts lack `installSection` and can no longer load this plugin). Verified against the host's real module graph: namespace `web-fetch-playwright` registers, the `playwright` fetch provider lands in `ctx.web`, and a committed settings change reaches the provider's config thunk; the full suite (126 tests) stays green.

- **Normal pages of Cloudflare-Bot-Management sites no longer misclassify as challenges** (badcase: `https://openrouter.ai/openai/gpt-6-astra-pro`). Cloudflare injects its passive JavaScript-Detections (JSD) telemetry into EVERY normal page of a protected zone — either as a direct `<script src="/cdn-cgi/challenge-platform/scripts/jsd/main.js">` or as that URL strung inside a hidden-1x1-iframe bootstrap's inline script text. The URL embeds the `/cdn-cgi/challenge-platform/` prefix, so the content-level marker scan read every such plain-200 real-content page as an interstitial; the live DOM probe then correctly said "not challenged", but the chained-round recheck re-ran the same false positive and overrode it, burning the whole wait budget and all retries and failing with `WEB_FETCH_CHALLENGE` ("last status 200"). The classifier now strips the `scripts/jsd/` telemetry directory before the challenge-platform prefix check (`classifyChallengeHtml`) and the DOM probe excludes it from its script-src scan (`CHALLENGE_DOM_PROBE`); the bare `/cdn-cgi/scripts/jsd/main.js` marker left the list entirely — it is telemetry in every spelling. Real interstitials still classify: they load orchestrate scripts (`/cdn-cgi/challenge-platform/h/…`) plus `window._cf_chl_opt` / `#challenge-*` / the title family, none of which live under `scripts/jsd/` (regression-tested, including an interstitial that carries the JSD script alongside its own orchestrate scripts). Verified live: the openrouter.ai badcase and nowsecure.nl both return their real articles now, and the full suite (126 tests incl. real-browser challenge integration) stays green.

### Removed

- `dsh.plugin.json`, the standalone plugin manifest. Its content was fully redundant with what the host already reads from `package.json` (the `dsh.*` fields plus `cordis.patch.yml` via `dsh.bundle.patch`), and as a second version-carrying file it had already drifted once (0.2.4's lockstep note) — the package manifest is now the single version source. The stale `"dsh.plugin.json"` entry is gone from the `files` list too, so the published tarball no longer claims a file it does not carry.

## [0.2.6] - 2026-08-27

### Fixed

- **Windows `$PATH` discovery works** (issue #1): `findOnPath` split `process.env.PATH` on a literal `:`, but Windows joins PATH entries with `;` — the whole variable read as one bogus directory, so auto-discovering a `playwright` executable (blank `playwrightPath`) never found anything and silently fell through to the bundled `playwright-core`. It now splits on Node's `path.delimiter`, and a regression test scans a multi-directory PATH with the probe in a non-first entry (the case both Windows reproducers in the issue hit).
- **`pnpm build` is cross-platform** (issue #1): the build script cleaned `lib/` with `rm -rf`, which does not exist on Windows PowerShell — `'rm' is not recognized` killed the build before TypeScript declarations or tsdown ever ran, and since `prepare` runs the same script, installing from a git checkout failed on Windows too. The clean step is now `node -e "require('node:fs').rmSync('lib',{recursive:true,force:true})"`, which works everywhere Node does (a follow-up `scripts/clean.mjs` was considered and dropped to keep the pipeline in one place; tsdown's own `clean` cannot replace it — it runs after `tsc` and would delete the declarations just emitted).
- CI now runs the full check (install, typecheck, test, build) on `windows-latest` alongside `ubuntu-latest`, Node 22/24 — so the PATH-split and build-script regressions above cannot land again unnoticed. The tarball content verification stays Linux-only (`/tmp` + `tar`/`grep` piping); it checks npm packaging, not platform behavior.
- Known Windows limitation, documented rather than fixed here: npm/pnpm global installs expose `playwright` as `.cmd`/`.ps1` shims whose upward walk cannot find the package root, so PATH auto-discovery may still land on the bundled core. Setting `playwrightPath` to the package root or a browser executable selects the intended installation; PATHEXT-aware probing is tracked as a follow-up.

## [0.2.5] - 2026-08-25

### Added

- **Bounded Cloudflare-challenge wait** (issue #2): when a navigation lands on a challenge interstitial, the fetch now keeps the **same page and browser context** and waits for the browser's own verification to clear it, instead of returning the interstitial as content (the behavior before this release — with a strict site that meant "Just a moment…" as markdown within ~1s, the real article never captured even though the browser would have passed the check seconds later).
  - Detection is layered with a suspicion gate: the documented `cf-mitigated: challenge` response header (set on every challenge page type), then 403/503 HTML from a `server: cloudflare` edge, then content-level markers — the localized interstitial title family ("Just a moment...", "请稍候…", "Минутку…", …) plus structural markers (`/cdn-cgi/challenge-platform/` scripts, `#challenge-*` elements, `cf-chl-widget-` frames, `window._cf_chl_opt`, the `.footer .footer-inner .ray-id` footer). Markers are attribute/assignment-shaped so an article that merely quotes them stays clean, and the content tier only runs on challenge-compatible responses (`isChallengeCompatibleResponse`: 403/429/503, or `server: cloudflare` / `cf-ray` present) — interstitials never ship a plain 200, so a normal article cannot be misread as a challenge (and normal fetches skip the extra content read entirely). Hard-block pages ("Attention Required!", "you have been blocked" + a `cf-headline`/`cf-error-details` layout) classify separately and fail immediately.
  - During the wait the provider tracks the **last main-frame navigation response** (the real page reloads in after the clear) and probes the live DOM every 500ms, so SPA-style clears (content swapped with no navigation) are captured too; a probe that throws mid-navigation (context destroyed) counts as "still challenged". A clear that lands on a *chained* round (JS test → Turnstile interstitial) is caught by a settled-DOM recheck — content-level, deliberately, so SPA clears whose response stays 403 forever still pass — and consumes one of the retries.
  - Knobs: `challengeWaitMs` (0–60000, default 15000; **0 disables the whole path and restores the exact pre-0.2.5 behavior**) and `challengeRetries` (0–3, default 1 — a same-tab re-navigation whose context keeps any clearance cookies the browser earned). Everything stays inside the 45s per-fetch deadline with a finish reserve; on exhaustion the fetch fails with the new provider-specific `WEB_FETCH_CHALLENGE` code (the web seam's open-string `code` tolerates provider codes) naming the site, budget, and last challenge status.
  - Cookie lifecycle is unchanged by design: isolated fetches' clearance dies with their context (verified: a second isolated fetch is challenged again), profile-mode clearance stays in the remote browser's own profile (verified: a second profile fetch skips the challenge); nothing is exported, copied, or manufactured. No clicking, no CAPTCHA answers, no fingerprint spoofing.
  - Settings card gains a *Cloudflare challenge wait (ms)* number field; `scripts/challenge-demo.mjs` runs a local simulated strict edge through the baseline and the feature for a before/after printout.
- New exports: `classifyChallengeResponse`, `classifyChallengeHtml`, `isChallengeCompatibleResponse`, `CHALLENGE_DOM_PROBE`, `CHALLENGE_TITLE_RE`, `CHALLENGE_POLL_INTERVAL_MS`, `CHALLENGE_FINISH_RESERVE_MS`, `WEB_FETCH_CHALLENGE_CODE`, `DEFAULT_CHALLENGE_WAIT_MS`, `DEFAULT_CHALLENGE_RETRIES`, `effectiveChallengeWaitMs`, `effectiveChallengeRetries`, and the `ChallengeVerdict` type.

## [0.2.4] - 2026-08-25

### Fixed

- Denoise now elides inline `data:` image payloads (`data:image/png;base64,...`) to size placeholders like `![alt](data:image/png;base64,...8.9KB)`. Build tools (Docusaurus/webpack) inline images above a size cutoff straight into the HTML; they survived Readability, DOMPurify, and Turndown as raw base64 — on the onlyoffice.com docs events page that was **65% of the returned body** (100k chars, truncated at the cap). With the placeholder the same page returns 41.8k chars complete. The elision happens in the DOM before extraction, so both the article and whole-document fallback paths apply it; it runs under the denoise toggle only (raw-HTML mode is untouched) and keeps alt text, MIME type, and the approximate size.
- `dsh.plugin.json` version had drifted (still 0.2.2 after the 0.2.3 release); both manifests now move in lockstep at 0.2.4.

## [0.2.3] - 2026-08-24

### Fixed

- The bundle layer no longer pins `searchProvider: deepseek-official` on the `web` row. The pin out-ranked every later layer, so a user's own search-provider bundle could register and stay healthy yet never be selected — and `$DSH_WEB_SEARCH_PROVIDER` was dead config too (the row's config beat the env). The row's whole config is still replaced by the patch (no deep merge), so `searchProvider` is now simply **omitted**: with the base bundle's single registered search provider, auto-selection picks it exactly as before, while any later layer — a user search bundle, the profile/home `cordis.patch.yml`, or `$DSH_WEB_SEARCH_PROVIDER` — is free to pin search. Two usable search providers with no explicit selection still fail loud (`WEB_PROVIDER_AMBIGUOUS`) instead of guessing. Fetch stays pinned to `playwright`; this bundle owns fetch, not search.

## [0.2.2] - 2026-08-24

### Added

- CDP context modes: a new `shareBrowserContext` setting (checkbox *Share the browser context (profile logins)* nested under the Remote CDP option in the plugin-configuration card, default **on**) selects how each CDP fetch is scoped. **Profile mode** (default): each fetch is a tab in the remote browser's default context — its real profile — so cookies/localStorage are shared and the browser's persistent logins apply; the tab closes when the fetch ends, the shared context never closes. **Isolated mode** (unchecked): the previous behavior — a fresh incognito-like context per fetch.
- `effectiveContextMode(config)` and the exported `CdpContextMode` / `CdpAcquireMode` types.
- Popup guard: popups a fetched page spawns (`window.open`) are closed so no tab outlives its fetch in the remote browser.

### Changed

- The fetch lease is now page-scoped: `CdpLease` carries `page` + `persistent`, `CdpConnectionPool.acquire` takes a mode, and `release` closes only what the lease owns (page always; context unless it is the remote default context). The connection-management core (ensure/connect/watch/drop/dispose) is unchanged — a `browser.close()` on a CDP handle only disconnects, so the remote browser always survives.
- Resource-subrequest filtering moved from context level to **page level**, so profile mode never intercepts tabs it does not own (an operator's manual tabs in the same context).
- Local-backend pages are closed explicitly on teardown (previously the page relied on its context's close to take it down).

### Fixed

- Local sessions now close in a defined order — page, context, browser — each grace-bounded, instead of leaving the page to the context-close side effect.
- Partial-failure leaks: an isolated lease whose `newPage()` fails on a live connection now closes the context it just created (it previously stayed open until the whole connection went away), and the local backend closes its launched browser when `newContext()`/`newPage()` fail after a successful launch (a whole Chromium previously stayed running).

### Security

- Profile mode is a semantic upgrade: fetched pages see the remote browser's logged-in identity, and requests they goad the agent into carry its session cookies. README (en/zh) documents the risk notes and the persistent-`user-data-dir` browser setup; the disclosure adds a credentialed-fetch permission entry.

## [0.2.0] - 2026-08-21

### Changed

- CDP backend architecture: instead of one `connectOverCDP` per fetch, the provider now keeps a **single shared connection** to the remote browser for its lifetime; each fetch leases an isolated context (a tab) and closes only that. Reconnects automatically when the connection drops or the configured endpoint changes; the connection is dropped on plugin unload. Concurrent fetches therefore cost tabs, not connections or browsers.
- Concurrency is backend-priced: `maxConcurrency` is now optional with backend-dependent defaults — **4** for local (each slot launches a whole Chromium) and **50** for CDP (each slot is a tab in the already-running browser), range widened to 1–200. The settings card explains the auto default; an explicit value still wins.

### Fixed

- `web fetch aborted while waiting for a free browser slot` no longer surfaces as the common failure under parallel `web_fetch` bursts: the CDP default alone covers 50 concurrent tabs, and a queued fetch that gets no slot within 20s fails fast with `WEB_FETCH_TIMEOUT` plus a retry/`maxConcurrency` hint instead of hanging until an abort mislabels it.
- Queue-wait errors translate through the standard taxonomy: the provider's own deadline expiring while queued reports `WEB_FETCH_TIMEOUT`, and a caller cancelling a queued fetch keeps the precise slot message under `WEB_ABORTED`.
- Cleanup hardening: context/browser closes in the fetch teardown are grace-bounded (2s), so a wedged Playwright close can no longer pin a concurrency slot forever (which previously made every later fetch die on the queue), and a queued fetch that fails to acquire never releases a phantom slot.

### Added

- `CdpConnectionPool` (exported): the shared-connection core — one connect under concurrent acquires, per-fetch context leases, liveness probes (`isConnected` + `disconnected`), single reconnect-and-retry, generation-guarded abandonment of connects made stale by an endpoint change or dispose.
- `effectiveMaxConcurrency(config)` and the `DEFAULT_MAX_CONCURRENCY_LOCAL` / `DEFAULT_MAX_CONCURRENCY_CDP` / `MAX_CONCURRENCY_CEILING` constants.
- Provider `dispose()` plus a `ctx.effect` teardown hook in the plugin entry that drops the shared CDP connection on unload.
- Tests: the CDP pool (8 cases), provider-level CDP behavior (one connection, tabs closed per fetch, 50-way tab burst, dead endpoint), queue cases, and a real-Chromium CDP integration smoke (debugging port, denoise fetch, 12-tab concurrent burst) that self-skips without a browser.
