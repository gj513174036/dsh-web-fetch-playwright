# 动作模型设计稿（待评审）

**状态**：设计稿；①「同意横幅的文本/角色候选」、②**目标识别与 `waitFor`**（0.2.18）、
③**`click` 与候选模型**（0.2.19）、④**`check`：回读确认的前置条件**（0.2.20）、
⑤**`waitFor` 状态类条件**（0.2.21）、⑥**`type`：写进输入框并让页面收到**（0.2.23）已按结论实现并测试。§9 是当初要拍板的清单，其第 4 条已被
ticket #4 推翻，修订记录见 §9 之后的「修订」小节。

**词汇**：用 `CONTEXT.md` 定下的词——目标、动作、意图、候选、发现、固化、重放、观察、抓包、动作录制。

## 1. 定位（依据 ADR-0001）

接口优先；动作模型服务两件事：① 挖不到干净接口的站点；② 一次性发现路径。因此
**它的第一职责是"确定性地重放"，不是"通用地理解页面"**。

## 2. 范围与非目标

- **范围**：目标识别、动作执行、失败语义、结果契约，以及发现阶段所需的「观察」接口设计。
- **非目标**：会话型规划（模型逐轮决策所需的会话生命周期）、新标签页、iframe/跨帧、录制器实现、
  任意脚本注入。这些都不在这份稿子里，也不在下一轮。

## 3. 目标（Target）

### 3.1 识别：URL 当钥匙

已核实：抓取请求只带 URL，没有任何调用方参数——所以"这次用哪个目标"只能由插件按 URL 判定。

| 规则 | 定论 |
| --- | --- |
| 写法 | 只有两种：`exact`（整串相等）、`prefix`（前缀） |
| 前缀边界 | 命中点必须落在 `/`、`?`、`#` 或串尾——`https://a.com/pr` **不**命中 `https://a.com/proxy` |
| 比对范围 | 默认只比 `scheme://host/path`，**忽略查询串与 hash**（同一页面带不同跟踪参数应命中同一目标） |
| 多条命中 | 最长（最具体）者赢；两条一样长 → **配置错误**，不猜 |
| 零命中 | **照常抓取**——不跑动作、不报错。这是绝大多数抓取的常态 |

### 3.2 存放

目标文件放在**仓库内**，插件设置里填它的**显式路径**。

事实依据：插件只能拿到进程 cwd（实测 `/workspace`），拿不到会话工作区（工作区服务按会话 header 归属，
而抓取这条路上不带会话身份）。所以不能靠"当前目录"隐式定位，必须显式配置。放仓库里意味着目标随代码
评审、随版本 diff——这正是它作为长期资产的价值所在。

### 3.3 文件形态草案

用 **JSON** 而不是 YAML：YAML 需要新增依赖，而本插件的依赖要**内联进 bundle**（曾因裸依赖导致加载
故障，见 CHANGELOG），为"能写注释"付这个代价不划算；何况固化产出的文件本来就是机器写的。这个权衡
写在明处，方便你否掉（§9-5）。

```json
{
  "targets": [
    {
      "name": "iherb-search-first-hit-detail",
      "match": { "kind": "prefix", "url": "https://cn.iherb.com/search" },
      "actions": [
        { "verb": "waitFor", "condition": { "kind": "text", "text": "搜索结果" } },
        { "verb": "click", "candidates": [ { "text": "商品标题" } ] }
      ]
    }
  ]
}
```

## 4. 动作模型

### 4.1 候选（Candidate）

候选 = 达成同一意图的一种方式；按序尝试，第一个"存在且可见"的生效，命中即止。

| 种类 | 写法 | 语义 | 现状 |
| --- | --- | --- | --- |
| 选择器 | `{ "selector": "#onetrust-accept-btn-handler" }` | 直接查节点 | **已实现**（同意横幅；`click` 一等候选） |
| 文本 | `{ "text": "全部接受" }` | 按可访问名**相等**匹配（去首尾、折叠空白、不分大小写） | **已实现**（同意横幅；`click` 一等候选） |
| 角色 | `{ "role": "button", "name": "接受" }` | 按角色 + 可访问名匹配 | **已实现**（`click`；见下方修订） |

说明：同意横幅的 `text` 候选**已经扫描** `[role="button"]` 与提交型输入框，所以当初"角色"只是
**找控件的方式**。§9-4 曾据此不把它升格为候选种类；ticket #4 推翻了这一条——理由是 ADR-0002 的候选
清单本就写着"CSS selector, visible label, role"，而角色是"这个控件是什么"的独立说法，不该靠选择器
或标签去代理。修订记录见 §9 之后。

### 4.2 动词表（提案）

| 动词 | 它保证什么 | 参数 | 失败意味着 | 重放是否需要 | 现状 |
| --- | --- | --- | --- | --- | --- |
| `click` | 某个控件被点击 | `candidates`（有序） | 所有候选都没命中 → 失败 | 是 | **已实现**（0.2.19） |
| `type` | 内容被写进输入框 | `candidates` + `value` | 找不到输入框 → 失败 | 是 | **已实现**（0.2.23） |
| `press` | 某个键被按下 | `key`（Enter / Tab / Escape …） | 极少失败 | 是（回车提交搜索） | 未实现，无站点逼出 |
| `scroll` | 懒加载内容出现 | 目标：文档底部、或某个候选 | 没到底 → 建议标 `optional` | 是（长列表） | 未实现，无站点逼出 |
| `check` | 某个前置条件被满足（勾选/选中） | `candidates`（**指向可见控件**，不是隐藏的 input）+ 目标状态 | 状态无法置为真 → 失败；**必须回读确认** | 是（同意闸门、筛选器） | **已实现**（0.2.20） |
| `waitFor` | 一个条件成立 | 见 §4.4 | 超时 → 失败 | 是（这其实是"成功判据"） | **已实现**（0.2.18） |

### 4.3 刻意排除的动词（以及为什么）

| 不做 | 理由 |
| --- | --- |
| `goto` | 抓取本身就是导航；配方里再塞一个 URL 会让"这次抓的是哪一页"含糊，而 URL 正是我们选目标的钥匙 |
| `evaluate` / 任意脚本 | 放开任意 JS 等于把"可评审的配方"变成"不可评审的代码"，还带越权风险；真要写代码就该去写爬虫 |
| `screenshot` / 写文件 | 不是这个能力的职责（要图片走抓包 + 直连，已实现） |
| `hover` | 先不给：绝大多数"悬停出菜单"也能用 `click` 覆盖，等真实站点逼我们加 |
| `select` | 原生下拉越来越少，自定义控件用 `click` 即可 |
| `frame` | 与 iframe 边界一起推迟 |

### 4.4 `waitFor` 的条件种类

`text`（某可见文本出现/消失）· `url`（URL 变化或匹配）· **`response`（某 URL 的响应到达，0.2.26 实现）** ·
`time`（固定等待，仍受总预算约束）· **`state`（一串候选之上的状态：全部选中/未选/可用/禁用，0.2.21 实现）**。

五种都已实现。`response` 最有价值：它是"数据已经到了"的直接信号，比等 DOM 结构稳得多——这也正是 ADR-0002
那条"瞄准更稳定的层"在等待上的体现。它写的是 `{ "kind": "response", "match": { "kind": "prefix" | "exact", "url": … } }`
——与目标**同一个 match 子句、同一段解析代码**；没有 `absent`，"响应一直不来"本来就是这一步的预算。语义见 §18。

## 5. 失败语义

- **每一步都要有后置条件，并且回读确认。** "点到了" ≠ "做成了"：booking.com 的同意闸门就是这样被抓到的——
  控件点得中、事件也发出去了，但页面毫无变化，而当时没有任何回读去发现这件事。没有后置条件的步骤等于
  假成功，而假成功正是本项目反复吃亏的那一类错误。
- **默认响亮失败**：任何非 `optional` 的步骤失败 → 整次抓取失败，错误里带**第几步**、**哪个动词**、
  **哪条候选/哪个条件**、**当时的 URL**。**绝不返回半成品页面冒充成功**——iHerb 那次"Cookie 横幅顶掉
  商品正文"就是静默返回错东西的代价。
- **单步 `optional: true`** 是唯一逃生口（典型用途：关掉一个可能出现也可能不出现的弹窗）。
- **零目标命中不是失败**（§3.1）：那是常态，不能变成错误。
- **预算**：一次抓取 45s（工具层上限 30s）；`waitFor` 用自己条件的超时；超预算即失败
  并说明卡在哪一步。每步默认上限取 10s（可调，属实现参数，不是设计约束）。

## 6. 结果契约（动作之后报什么）

已核实：结果类型是**封闭的**——`dsh-web` 拥有 `url` / `statusCode` / `body.content` / `truncated`，
工具层只投影这几项，**插件无法新增结果字段**。所以：

- `statusCode` 与 `url` **跟随动作之后的最终文档**（重新取，而不是沿用首次响应）；
- "跑过动作、最终落在哪一页"只能写进**正文**，做法是在正文最前面加一行引用块，例如：

  > 动作：waitFor 文本「搜索结果」→ click 文本「商品标题」→ 最终文档 https://… （HTTP 200）

  只在动作确实跑过时出现。
- **已否的备选**：只写 stderr 日志。理由：调用方看不到日志，而"我拿到的是哪一页"必须能被调用方看见。

## 7. 观察（Observe）——发现阶段用，重放不需要

给规划者读回的页面状态，v1 提案。**预置条件住在状态里，不在标签里**——booking.com 的同意闸门证明了这一点：
页面上写着"需您同意"、列了 5 项、还有一个"全选"，但 5 个 `<input>` 是**隐藏的**，人点的是外面的可视图
标签；用 DOM `.click()` 改 `checked` 会被 React 还原，于是"同意"按钮毫无反应。**光有标签读不出这套流程**，
必须能看到"哪些控件是勾选状态、哪些是禁用状态、哪个是可见宿主"——这正是观察要回读的东西。

1. 最终 URL 与标题；
2. 可见的可交互控件（按重要性取前 N 个）：标签 + 一个候选描述符——这就是"下一步能点什么"；
3. 可见文本的开头若干字符（用来判断"这是哪一页"）；
4. 自上一次观察以来文档是否变化。

**明确不给**：截图、完整 DOM、样式。给模型的应该是"能做什么"，而不是"页面长什么样"。

## 8. 已知边界

~~单标签（动作弹出的新标签页会被 popup 守卫关掉）~~ → **标了 `opensPage` 的点击可以接管它开出来的页面**（0.2.25，见 §17）· 只处理主文档（无 iframe/跨帧）· 动作依赖 `evaluate`
（缺失则带动作的目标响亮失败）· 不支持正则匹配 · **响应条件只认"动作开始之后"到达的响应**（加载阶段页面自己
取到的数据，要用文本或状态条件说）· 不改变现有并发与重试语义（动作只让单次抓取更久，
仍受同一队列与预算约束）。

## 11. 实施顺序（已定）

1. **先探针**（ADR-0001 的直接推论）：拿一个真实站点跑一遍「抓取 → 抓包 → 找接口」。结论只有两种，
   两种都有价值——挖到干净接口则该站点**不需要**动作模型（最省的结果）；挖不到则记下它到底需要哪几个
   动词与条件。
2. **只实现探针逼出来的那部分**，用它跑通「发现 → 固化 → 重放」这条链。
3. **再补全其余动词**：已达成的共识是**以后要跑的站点种类会很多**，完整能力最终是需要的；而按 1、2 的
   顺序补全时，动词表已被真实站点验证过，返工风险基本消失。

### 这次铺开逼出来的动词

| 动词 | 来自哪个站点 | 为什么 |
| --- | --- | --- |
| `waitFor` | NMPA、Booking 同意插页 | 结果/跳转是异步出现的，必须先等条件成立 |
| `click` | NMPA、Booking 同意插页 | 表单提交、接受按钮 |
| `type` | NMPA（查询框要填关键字） | 视其表单实现而定 |
| `press` / `scroll` | **本次无人逼出** | 按 §11 先不做，等真实站点逼出来 |
| `response` 条件 | ~~本次无人逼出~~ → **被正式路径逼出来了**（NMPA 的提交由 `…/data/nmpadata/countNums` 回答） | 0.2.26 实现，见 §18。当时"文本条件够用"的判断，其实是拿结果表里恰好出现的某个药名当代理 |

**结论：§11 第 2 步只需实现 `waitFor` + `click`，`type` 视 NMPA 表单而定。** 这就是"只实现被逼出来的
动词"的具体答案——而不是先把五个动词都写出来。

### 不是动作模型能解决的三类

| 类别 | 例子 | 真正的解法 |
| --- | --- | --- |
| 登录后才有数据 | JD、知乎、GitHub 设置页 | **会话**：共享真实 profile（前提是那个 profile 确实登录了该站），或单独的登录步骤；动作模型在这里帮不上忙 |
| 同意**插页**（整页跳转，不是横幅） | Booking.com | 现有能力只处理**横幅**；整页插页是个缺口，值得单列（后续：识别插页 → 点击 → 回到目标页） |
| 内容在二进制里 | PDF | 二进制/下载路径；当前 `web_fetch` 拒绝非 HTML |

### 探针工具自身的两个局限（照实记）

1. **`contentChars ≥ 2000` 会把"外壳很厚的首页"误判成"已拿到内容"**：Swanson 正文 4195 字，多数是导航与
   页脚，商品其实没在里面。判词不能替代人看一眼。
2. **分不清"数据接口"与"防护信标"**：FDA 那两个随机路径 JSON 被计成接口，实际是 WAF 噪音。

这两条都指向同一件事：**判词只作分流线索**；真正的结论来自"要长期跑的站点走 `web_fetch` + `netdump`
的正式路径，并且像 Swanson 那样——探针说'接口带签名、只能驱动 DOM'，而 ADR-0001 的纪律让我们多花
一次 `curl` 就找到了 `/products.json`。"

## 12. 由 booking.com 同意闸门逼出来的新增项

一次真机排查（五种交互方式、逐次回读状态）得到的结论，按 §11 的纪律记下来：

| 新增项 | 证据 |
| --- | --- |
| **动词 `check`** | 页面要求 5 项全部勾选后才允许继续；只做 `click` 覆盖不了"满足前置条件"这件事 |
| **`waitFor` 增加状态类条件** | 需要"这些控件全部为选中"、"该按钮可用"这类判据；纯文本条件表达不了 |
| **`click`/`check` 必须指向可见控件** | 5 个 `<input type="checkbox">` 是隐藏的；`locator.check()` 对它们全部超时，真实鼠标点在它们的 `<label>` 上才生效 |
| **每步回读验证（§5）** | 对隐藏 input 做 DOM `.click()` 会把 `checked` 改成真，但被 React 还原——不回读就看不出"没生效" |
| **观察（§7）是推断的前提** | "有全选"、"5 项是必备"、"要点外面的标签"这三件事只能从**读页面**得到；固定配方在写下来之前无法凭空包含它们 |

**仍然未解决的一点（照实记）**：勾齐 5 项后点击"同意"，页面依旧停在闸门（`stillGate: true`，正文 510 字）。
三种点击方式（DOM `.click()`、CDP `Input.dispatchMouseEvent`、Playwright 真实输入）都试过，均未过关。
剩余怀疑对象：该标签页在 CDP 下**不是前台/聚焦**、站点自身的自动化检测、或更长的异步跳转——**我没有确定
是哪一种，所以不写成结论**。

> **更正（0.2.20，实现 `check` 之后重测）**：这一条**已不成立**。用 `check 全选` 把五项勾上、再 `click 同意`，
> 闸门会正常放行：`final document https://www.booking.com/index.zh-cn.html?... (HTTP 200)`，`stillGate false`。
> 当时失败的原因**不是**那三个怀疑对象，而是"勾上"这件事本身没做成：对隐藏 `input` 的 DOM `.click()` 会被
> React 还原（§12 第一条），而点 `<label>` 单独点、逐项点，与页面自己的"全选"语义不是一回事——只有把
> "点在 label 上 + 回读确认 + 等页面反应过来"做成一步，五项才真的进了页面的状态。结论：**动词 `check`
> 才是那条闸门的解**，不是换一种点击方式。

## 13. `click` 实现时定下的细节（0.2.19）

§4.1、§5 定了候选与失败语义；真正写下来时又逼出五条，照 §11 的纪律记下：

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| **点击不承诺效果** | `click` 只报"哪条候选落地了"；跟在它后面的 `waitFor` 才是判据。目标以 `click` 结尾时，摘要里那步标成 **`clicked (unverified)`** | 一次点击在不同页面上做的事不同，任何"通用后置条件"都只能是猜（§5）。原文说"每步都要有后置条件"，而这条动词做不到——所以把缺口**显示出来**，而不是假装补上 |
| **`unverified` 的判据是"后面那个 `waitFor` 真的从假变真"** | 点击后面的第一个非 `time` 的 `waitFor` 报了 `met`，**且它在点击之前并不成立** → `clicked`；否则 `unverified`。文本条件在**点击脚本内部、点击之前**读一次（只有页面知道自己的文本）；`url` 条件由 runner 用 `page.url()` 直接算 | `time` 只说明时钟走过；被跳过的 `optional` 等待什么都没确认；而一个**点击前就已经成立**的等待同样证明不了这次点击做了什么——"点了"与"页面因此变了"之间差的正是这一步 |
| **点击前验可达性，四问合一** | 存在、占布局（自己或经由 `<label>`）、没被盖住（`elementFromPoint` 打在**人真正会点到的那个元素**上）、没禁用（`disabled`、`aria-disabled="true"`，以及 `<fieldset disabled>` 里的后代——它自己没有 `disabled`，点了也不会响应） | §12 已经证明"点得中"与"生效"是两件事；这里是它的前置一半。#5 的 `check` 直接复用同一套 `reachabilityOf`，不另写一份 |
| **导航撕掉执行上下文不算失败** | `evaluate` 因导航被销毁时，报 `clicked-unreported`（"点发出去了，页面在它开口前就走了"） | 否则**每一次点链接**都会被判成"控件不可达"。这是实现层的现实约束，不是放宽语义：判据仍是后面那个 `waitFor` |
| **答案随页面一起死掉时，不许借后面那个等待的功劳** | 上面那种情况下点击前的状态也没了：**URL 变了**（页面确实动过）→ 后面的 `waitFor` 可以判；**URL 没变** + 后面是文本条件 → 标 `unverified` | 状态没了就是没了。URL 变化是独立证据，文本没有独立证据——这时报 `clicked` 正是本项目最不能接受的那类"看起来成了" |
| **点的是页内 `.click()`** | 不用 `locator.click()` / 真实鼠标：`evaluate` 已是本抽象既有的脚本缝（挑战探测、同意横幅都用它），且它在各后端上都是可选的 | 与 §12 的实测一致：booking 的隐藏 input 用 DOM `.click()` 会被 React 还原，而点它外面的 `<label>` 有效。信任事件（`isTrusted`）这一层没做，真实站点逼到时再单列一张票——不预先为假想站点付费 |

| **弹窗是边界，不是工作区** | 点 `target="_blank"` 的链接：点击确实发生，但导航落在新标签页、被弹窗守卫关掉，本次抓取正在读的那个页面并没有动 → 后面的判据不成立，抓取响亮失败；若配方以这个点击结尾，摘要标 `unverified` | 真机实测（163.com「新闻」、百度「新闻」、gov.cn「要闻」都是 `_blank`）。§8 早就写了"单标签"；这里只是把它的具体表现记下来。跟着新标签走要另开一张票，不在这里偷偷加 |

**同批定下的候选考虑范围**（`text` / `role` 两类候选扫描的控件集合）：
`button, a[href], input, select, textarea, label, summary, [role], [contenteditable="true"]`。
选择器候选不受此限——它查什么就是什么。范围故意包含 `label` 与输入框：前者是人点隐藏控件的方式，
后者是 #6 `type` 要写的目标，而"第一个可达者胜 + 摘要里点名落了哪条候选"这两件事，让范围宽不至于
变成隐患。

## 14. 由 #5 `check` 逼出来的五条（0.2.20）

真机重放（booking.com 的同意闸门，`check` → `click` → `waitFor`）暴露了下面这些，按 §11 的纪律记下来：

| 决定 | 内容 | 证据 |
| --- | --- | --- |
| **"占布局"不等于"点得中"：还要问它的 `<label>`** | `hitTargetOf` 先问控件本身（占布局且没被盖住），不行再问**转发点击给它的 `<label>`**（同样两问）。这不是"隐藏 input 的兜底"，而是常规路径 | 闸门今天的真实形状：`<input type="checkbox">` 是 **1×1 px**（所以"占布局"成立），它的 `<label for=…>` 是 **897×20**，而 `elementFromPoint` 打在 input 中心时命中的是 label 画上去的 `<span>`——按旧规则判定"被盖住"，五项一个都勾不上 |
| **回读必须等页面反应过来** | 点击后等一个 `requestAnimationFrame` + 一个 tick 再读，并且读**页面现在展示的那个控件**（节点还在就读它，被换掉就按候选重新解析） | React 会在事件之后重渲染；点击后立刻读会读到"改过了"，而那正是 §12 第一条的假象 |
| **幂等：已在目标状态就不动它** | 先读、后决定：已是目标状态 → 不点，摘要写 `already checked` | 同一配方连跑两次：第二次 `changed:false`，观察里 `uncheckedCheckboxes` 保持 0——**没有被切回去** |
| **`check` 只认回读，不认点击** | 点完读不到目标状态（页面还原 / 控件消失 / 读到的是另一个状态）→ 整步失败；读了但状态读不到（导航把上下文撕了）→ 也算没满足，绝不"假定它成立" | 单元测试覆盖还原与消失两条；`unverified` 是本动词唯一的"诚实缺口"出口 |
| **`waitFor` 的 `absent` URL 条件要写页面的完整路径** | 写成路径的**非边界前缀**（如 `…/pipl_consent` 之于 `…/pipl_consent.zh-cn.html`）时，条件**恒真**、步骤立刻"met"，于是闸门页会被当成目标页返回——一次静默的错答案 | 实测踩到：摘要写着 `to have left … — met`，而 `page.url()` 仍是闸门。改写为完整路径后，条件真的等到离开才成立 |

## 15. 由 #8 状态类条件逼出来的四条（0.2.21）

真机重放（booking.com 的五个同意框：`全部未选` → `check 全选` → `全部选中`）定下了这几条：

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| **作用域 = 第一条"答得上"的候选** | 候选按配方顺序走，**第一条**能给出答案的（它名下至少有一个控件能被问这个问题）定下集合，后面的不再看 | 与所有动词同一条有序候选规则；若取并集，一条宽泛的兜底候选会**悄悄扩大**条件所谈的集合，而条件的真假就跟着变了 |
| **答不上的控件被剔除，而不是算作"未选中"** | `<label>` 没有状态、文本框的 `checked` 恒为 `false`——把它们算进来会让"不是复选框的东西"替条件做决定。一条候选名下**一个都答不上**时，继续走下一条候选 | 与 `check` 的 `accept` 过滤器同一条道理（§14） |
| **不问可达性** | 状态问题只问"它现在是不是这个状态"：闸门那 5 个 1×1、被自己的 label 盖住的 input 照样能读 | "能不能点中"和"勾没勾上"是两件事（§14）；混在一起会让条件永远不成立 |
| **匹配不到不算立刻失败** | 页面可能还在渲染，所以轮询继续问，直到这一步的预算用尽才失败，并且**带上它看到的东西**：`all checked over selector "…": 3 of 5 controls in … are not checked (e.g. "全选")`。每次读取都受本步剩余预算约束 | §5 的"响亮失败"要的是**说清看到什么**，而不是一句超时；同时一次卡住的读取不能活过这一步的上限 |

## 16. 由 #6 `type` 逼出来的四条（0.2.23）

真机重放（bing 的搜索框：写入 → 提交 → 结果 URL 带着那个查询词）定下了这几条：

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| **写值要走原型链上的 setter** | `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, value)`，而不是 `el.value = value` | 受控组件会在元素上装一个自己的 `value` 属性：它的 setter 会顺手更新自己的"上次看到的值"，于是**改动看起来没发生过**，随后的 `input` 事件被框架无视。走原型链上的 setter 只改真实值、把 tracker 落在后面，页面才会看到差异 |
| **写完要"喊一声"** | 聚焦 → 写值 → 派发冒泡的 `input` 与 `change` | 只听 DOM 值、不听事件的写法是"点了一下但没点中"的同一类假成功（§5）。不逐字模拟按键：那需要 `press` 动词，而它要有自己的票 |
| **只写"人能写"的控件** | 复选框/单选框/`file`/`range`/`color`/`hidden`、原生 `<select>`、以及 `readonly`/`aria-readonly` 一律拒绝 | `readonly` 对 `click`/`check` 不是问题（点得中、也勾得上），所以它属于**本动词的准入条件**，而不是共享的可达性判定 |
| **写完要回读** | 与 `check` 同一套道理：等一帧再读，读的是**页面现在展示的那个控件**；不一致就失败并说清"写的是 X、它现在拿着 Y" | 受控组件会先接受改动、再按自己的状态重渲染回旧值（§14 同款）；"我写进去了"不等于"值在那儿"。至于页面拿这个值**去做什么**，仍是后面那个 `waitFor` 的事 |

## 17. 由 #10 接管"动作开出来的页面"逼出来的四条（0.2.25）

真机重放（NMPA 数据查询：点数据集磁贴 → 填关键词 → 提交 → 结果表在**新标签页**里）定下了这几条：

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| **`"opensPage": true` 是"预期"，不是"开关"** | 写了它而没开出页面 → 这一步失败并点名（`the step expects a page to open, and none did`） | 停在原地继续读，正是本项目反复拒绝的静默错答（§5）。预期写进配方，缺了就响亮失败 |
| **接管发生在"动作之前"注册的监听器里** | 等待器在点击**之前**挂上 `popup` 监听，第一个到达的页面被认领；认领发生在守卫的关闭之前（守卫的关闭延后一个 tick） | 页面可能在点击飞行途中就打开；监听挂晚了会漏掉它；而守卫必须仍有"没人认领就关掉"的行为（§8 的原意） |
| **之后的一切都属于被接管的页面** | 后续步骤、等待、以及抓取读取并描述的文档（URL/状态）都是那一页；被接管页的响应单独跟踪 | "跑过动作、最终落在哪一页"必须能被调用方看见（§6）——否则摘要说着新页面、正文却是旧页面 |
| **接管的标签页随抓取一起关闭** | 认领时登记进本次抓取；teardown 关闭它；**没被认领的**仍由守卫关掉 | 在 profile 模式下，一个漏掉的标签页会留在用户的真实浏览器里——守卫存在的唯一理由 |

同批记下的两条**页面事实**（不是模型问题，但会影响配方怎么写）：

- **`<a>` 没有 `href` 就既没有 link 角色、也不在候选控件集合里**（NMPA 的 36 个数据集磁贴就是这样），只有**选择器**候选够得着。
- **`observe` 会丢掉没有可访问名的控件**（NMPA 的提交按钮是纯图标、无名），所以报告里看不到它——配方只能靠选择器点名它。
- **文本条件比的是页面原始可见文本**，而 `observe` 的文本头是**折叠空白**后的：从观察里抄来的 `药品 Drugs` 在 DOM 里可能是 `药品\nDrugs`，于是条件不成立。挑不含内部空白的词。

## 18. 由 `response` 条件逼出来的五条（0.2.26）

§4.4 把 `response` 称作五种条件里最有价值的一种，附录 B 却记着它"本次无人逼出"、按 §11 推迟。**0.2.26 把它
补上了**——逼它的不是又一次铺开探针，而是 §11 第 1 步的正式路径（`web_fetch` + 抓包）在 NMPA 上留下的记录：
提交由一次 XHR 回答，`GET …/datasearch/data/nmpadata/countNums?…&searchValue=阿司匹林` →
`200 {"code":200,"data":[{"name":"境内生产药品","nums":924}]}`（抓包 `net-dumps/20260923T151255Z-8c6d-001`）。
当时配方等的是文本 `阿司匹林肠溶片`——那只是"结果表里恰好出现的某个药名"，不是"数据到了"本身。

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| **从动作开始就在听** | 运行开始时挂上响应监听并记住到达的 URL；**页面加载阶段取到的响应不算** | 响应是"动作之后发生了什么"的证据。数据若在动作之前就在手里，诚实的说法是文本/状态条件，而不是把旧的到达算成新的 |
| **一次等待认领一次到达** | 同一个接口等两次就需要两个响应 | 响应是**事件**而不是状态：分页列表"点下一页、再等同一个接口"时，若第一次的到达能满足第二次，就是本项目最不能接受的静默错答 |
| **点击前先读一次** | 与 `url` / `state` 同款：点击前手里有**尚未被任何等待消费**的匹配响应 → 等待仍可成立，但那个点击记 `clicked (unverified)` | "等待成立"与"点击被证明"是两件事（§5）；把手里已有的证据算成点击的功劳就是假成功。**已被此前等待消费的到达不算**——它不可能再被后面的等待消费（见下一条），把它算成"点击前就成立"会把一次真被点击引发的响应误判成未验证 |
| **监听挂在动作之前** | 点击飞行途中到达的响应必须被接住；`opensPage` 时新页面在**弹出那一刻**就开始听（认领之后还会再挂一次，`arm` 幂等） | 真实响应常在点击返回之前就落地；等 `waitFor` 才开始听会漏掉它——那会把一次真的成功变成超时 |
| **读不到就响亮失败，超时要点名最后一条** | 页面没有响应事件缝 → 这一步失败并说"页面读不到"；超时则附上**运行看到的最后一条响应 URL** | 没人听的等待不是"还没到"；而"页面其实在调别的接口"是配方作者最需要知道的一句话 |

配套的页面事实：**响应条件只看主文档所在的那个页面**（以及 `opensPage` 接管的那一页）——被接管的页面从
弹出那一刻起被监听，所以它加载时自己发的请求也在窗口内；反过来，**别的标签页的流量不算**（与抓包只认本次
抓取开的那个标签页是同一条纪律）。
